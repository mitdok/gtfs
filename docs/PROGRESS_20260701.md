## 2026-07-02 総括

この期間で、GTFS Studio は「GTFS zip を読み込んで編集・検証するデモ」から、
「公開候補を revision として保存し、証跡を集め、publish と smoke まで進める運用MVP」へ寄った。

特に進んだのは次の4点。

- Webの実務編集: 停留所、ダイヤ、運賃、shapeを一通り編集でき、shapeは地図上の頂点操作まで到達した。
- 公開ゲート: validator report、仕様ロック、実データ回帰summary、warning承認、revision保存、publish、public URL smokeを同じ画面に集約した。
- API運用: revision永続化、latest配信、publish状態遷移、warning承認保存、監査ログ、token、revision一覧のlimit/offset/status/statusCounts/detail取得が揃った。
- 証跡運用: `gtfs-regression`、`gtfs-anonymize`、回帰summary取込、公開チェックリスト、API運用手順、設計メモを文書化した。

直近の仕上げでは、API revision一覧を公開運用の入口として扱えるようにした。
単なるID選択ではなく、status、gate、acceptance、profile、日時、hash、状態別件数、ページ移動、詳細metadataを見てから、
公開中の版を再読込するか、未公開候補を確認するか、過去版として参照するかを判断できる。

ここから先は、コード量を増やすよりも、実データと運用環境で証跡を固める段階に入る。
優先度が高いのは、実データ候補の許諾レビュー、GitHub Actionsでのvalidator/golden/regression実績、DB/RBAC方針、
GTFS-RT TripUpdatesの実データ評価である。

## 得られた知見

revision は単なる保存先ではなく、編集セッションの文脈そのものになる。`projectId` と `revisionId` を画面ごとに持つと、warning承認、publish、smoke、再編集が分断されるため、App 全体で文脈を保持する必要がある。

warning承認は操作ログではなく、公開対象 artifact に紐づく metadata として扱うべき。revision保存と承認記録が別々に残ると、後から「どのzipに対する承認だったか」が曖昧になる。

公開ゲートはブラウザ内検証だけでは完結しない。validator report、回帰summary、仕様ロック、public URL smoke は外部証跡なので、Web UI にはそれらを取り込む明示的な導線が必要になる。

CLIとWebは入口が違っても、使う証跡は同じであるべき。`report.json`、`summary.json`、仕様ロック、warning承認、smoke結果を同じ公開判定へ流せるようにすると、運用手順の説明が簡潔になる。

revision一覧は最初から増える前提で扱う方がよい。今回 `limit`、`offset`、`status`、状態別件数、詳細metadata表示を入れたことでMVPの過読込は抑えられるが、次は cursor 化と revision比較を足すと、長期運用の一覧画面に接続しやすい。
