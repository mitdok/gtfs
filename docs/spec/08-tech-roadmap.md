# 08. 技術選定・アーキテクチャ・ロードマップ

## 8.1 アーキテクチャ概観

```
                 ┌─────────────┐        ┌──────────────────┐
   ブラウザ ───▶ │  SPA (Web)  │ ─────▶ │ 自前MapLibre地図基盤 │ スタイル/タイル（別資産）
                 │             │ ⇕アダプタ└──────────────────┘
                 └──────┬──────┘  ダイヤ表/地図編集/検証UI
                        │ REST/JSON (認証: OIDC)
                 ┌──────▼───────────────┐
                 │   API サーバ          │  CRUD / 検証 / 版管理
                 │   ┌───────────────┐   │
                 │   │ 取込ワーカー    │   │ xlsx/csv/zip 解析（非同期）
                 │   │ 出力ワーカー    │   │ gtfs.zip 生成（非同期）
                 │   │ 検証ワーカー    │   │ 構造/標準準拠検証
                 │   └───────────────┘   │
                 └───┬───────────┬───────┘
                     │           │
              ┌──────▼───┐  ┌────▼─────────┐
              │  RDB     │  │ オブジェクト  │  生成zip/版アーティファクト
              │(Postgres)│  │ ストレージ    │
              └──────────┘  └────┬─────────┘
                                 │
                          ┌──────▼──────┐
                          │  CDN/配信層  │  公開フィードURL（匿名・常時）
                          └─────────────┘

   GTFS-RT（フェーズ2）:  外部ソース ─▶ ingest ─▶ ホットストア(Redis) ─▶ RT配信層(.pb)
```

### 配信分離の要点
- 公開フィード（`gtfs.zip`）はオブジェクトストレージ＋CDNから配信し、**アプリ障害時も配信継続**。
- 「最新版エイリアス」はストレージ上のポインタ更新（または短TTLのリダイレクト）で実現。

## 8.2 技術スタック（確定）

フロントエンド・バックエンドとも **TypeScript**、DBは **PostgreSQL** で確定。言語を統一することで、ダイヤ展開・検証など中核ロジックをフロント/バックで共有しやすくする。OSSとして自己ホスティングしやすい構成（依存の軽さ・標準的なミドルウェア）を優先する。

| 層 | 採用 | 備考 |
|----|------|------|
| フロントエンド | **TypeScript + React**。ダイヤ表は仮想化テーブル（TanStack Table/Virtual）、地図は**自前MapLibre地図基盤を地図アダプタ経由で利用**（[02](./02-requirements.md) F-10 / [04](./04-screens.md) 4.4） | 地図基盤は別資産。UIはアダプタで疎結合 |
| バックエンド | **TypeScript（Node）**。NestJS等のフレームワークは別途確定 | ダイヤ展開・検証はフレームワーク非依存の純ロジックに分離 |
| DB | **PostgreSQL**（jsonb活用、空間は必要に応じPostGIS） | |
| 非同期処理 | ジョブキュー（取込/出力/検証） | Redis + ワーカー |
| ストレージ | S3互換オブジェクトストレージ | オンプレ時は MinIO 等で代替可 |
| 配信 | CDN（ETag/Cache-Control） | オンプレ時はリバースプロキシ＋キャッシュで代替可 |
| 認証 | OIDC（メール＋IdP連携） | RBAC自前 |
| 検証 | **ハイブリッド**: 自前ルール（層1・2、GTFS-JP固有・編集統合）＋ MobilityData Canonical GTFS Validator 内部実行（層3、標準準拠の最終確認） | 8.2.1 参照 |
| RT（P2） | Redis等ホットストア＋protobuf（gtfs-realtime） | |

### 8.2.1 検証アプローチ（ハイブリッドで確定）
「自前実装」か「標準バリデータ」かの二者択一ではなく、**役割分担で両方**を使う。

- **自前実装（層1・層2）**: 編集中のリアルタイム検証と、`*_jp.txt`・読み仮名などGTFS-JP固有ルールを担当。自分たちのデータモデルに密結合できるため、該当の便・停留所セルへ**ディープリンク**でジャンプできる。標準バリデータはGTFS-JP拡張を検証しないため、この層は必須。
- **標準バリデータ（層3）**: 出力した `gtfs.zip` に対し MobilityData Canonical GTFS Validatorの採用バージョンを**内部実行**し、国際標準準拠の権威ある最終チェックを行う。結果は検証結果画面(S-13)に統合表示。Java製のため、ワーカーからの別プロセス実行で連携する。バリデータ自体のバージョンアップに追従できるよう、採用バージョンと実行バージョンを版の検証結果に記録する。
- **プロファイル追加検証**: GTFS-JP v4、v3互換、Google Maps申請向け品質ゲートは [10-gtfs-compliance](./10-gtfs-compliance.md) のプロファイル定義で管理する。GTFS公式のRequiredとGoogle向け実務必須を混同しない。

> これにより「編集体験（自前）」と「お墨付き（標準）」を両取りする。詳細ルールは [06-gtfs-export](./06-gtfs-export.md) 6.5。

### 重要な実装方針
- **ダイヤ展開ロジック（pattern_stops→stop_times）と検証ロジックは、フレームワーク非依存の純粋関数として実装**し、単体テストを厚くする（本サービスの心臓部）。
- 出力は決定的（同一入力→同一バイト）にし、差分・回帰テストを容易化。
- GTFS-JPの項目定義は**設定（バージョン定義）駆動**にし、仕様改定をデータで吸収。

## 8.3 編集データと版の二層構成

- **ライブ編集データ**: 03章の正規化テーブル群。常時編集・自動保存。
- **版（FeedRevision）**: 公開のために確定したスナップショット（JSONスナップショット＋生成zip）。
- 公開＝版を作成し配信エイリアスを向ける。ロールバック＝エイリアスを過去版へ。
- これにより「編集途中でも公開中フィードは安定」を担保。

## 8.4 テスト戦略
- ダイヤ展開・時刻計算（24時超含む）の単体テスト。
- インポータ: 実際の西沢ツール各版・実フィードのサンプルでゴールデンテスト。
- 出力: 既知フィードを取込→出力し、標準バリデータでエラー0を確認する回帰テスト。
- 検証ルール: 各ルールにつき陽性/陰性ケース。

## 8.5 段階リリース計画（ロードマップ）

### フェーズ0: 基盤（PoC）
- 認証・組織・プロジェクトの最小実装。
- データモデル（03章）の確立。
- GTFS-JP zip のインポート → 内部モデル化 → そのまま再出力（ラウンドトリップ）が標準バリデータでエラー0。
- **マイルストン**: 「取り込んで出し直せる」ことの証明。

### フェーズ1: 西沢ツールWEB版（MVP・本命）
- 固定路線バスの静的GTFS-JP v4作成に範囲を絞る。
- 停留所/経路/パターン/ダイヤ/運行区分（S-05〜S-09）のWeb編集。
- ダイヤ表UI（S-08）— 西沢ツール体験の中核。
- 西沢ツール様式 xlsx のインポート。
- `agency.txt`, `stops.txt`, `routes.txt`, `trips.txt`, `stop_times.txt`, `calendar.txt`, `calendar_dates.txt`, `feed_info.txt`, `fare_attributes.txt`, `translations.txt` の生成を最優先に実装する。
- 均一運賃以外の`fare_rules.txt`、帰属表示用`attributions.txt`、簡易`shapes.txt`はMVP内で最小対応する。
- 検証（層1・層2・層3）＋`gtfs-jp-v4`/`google-transit-ready`公開ゲート。
- 版管理・安定URL配信・予約公開（S-14）。
- **マイルストン**: ゼロから/移行からGTFS-JPを作って公開でき、[11-release-acceptance](./11-release-acceptance.md) のA-01〜A-10が全件passする。

### フェーズ1.5: 運用品質
- 翻訳/読み仮名の拡充、運賃Fares v1、shape地図編集、差分・ロールバック、監査ログ、通知。
- `gtfs-jp-v3-legacy`の再出力品質を高め、v3→v4移行警告を整備する。
- 地図編集（停留所ピン/shape頂点）を**地図アダプタ(4.4)経由で自前MapLibre地図基盤**に接続。地図基盤の仕様確定までは仮実装で先行。
- 大規模フィードでの性能最適化。

### フェーズ2: GTFS-RT
- 2-a Alert手動配信 → 2-b 外部RT中継 → 2-c 突合エンジン（07章）。

### フェーズ3: 拡張
- **GTFS-Flex対応**: オンデマンド型交通（デマンドバス・乗合タクシー）の記述。採用時点のGTFS Schedule Reference、GTFS-JP文書体系、標準バリデータ対応状況を確認して仕様ロックを追加する。
- **GTFS-Fares v2対応**: 距離制・ゾーン制等の複雑な運賃の記述。採用時点の公式仕様と標準バリデータ対応状況を確認して実装する。
- map matchingによるshape生成、テンプレート/AI入力補助、ダイヤ作成支援等。

## 8.6 リスクと対策

| リスク | 対策 |
|--------|------|
| GTFS-JP仕様改定への追従 | プロファイル/項目定義の設定駆動化 |
| 西沢ツール様式の版差・表記揺れ | 様式バージョン判定＋ゴールデンテスト、取込時の差分確認UI |
| ダイヤ大規模時の編集性能 | 仮想化テーブル、パターン中心モデルで行数圧縮、サーバーページング |
| 公開フィードの可用性 | 配信をストレージ/CDNへ分離、アプリと独立 |
| RT入力ソースの多様性 | アダプタ方式＋mapping_configで吸収、まずAlertから |
| 公開データの正確性責任 | 検証ゲート、版・監査ログ、利用ライセンス明示 |
| 自前地図基盤の仕様が未確定 | 地図アダプタ(4.4)で疎結合化。仮実装で編集機能を先行開発し、確定後はアダプタ内のみ更新。地図無しでも数値編集で成立(F-10-5) |
| 既存コミュニティとの分断（独自路線がコミュニティ分裂・車輪の再発明と受け取られる） | **立ち上げ初期に日本バス情報協会・西澤氏側へ連携を打診**（8.8の最優先事項）。リポジトリとは競合せず連携(F-7-7)、出典・敬意の明記(1.4) |
| 既存陣営からv4対応の後継作成ツールが登場しニッチが縮小 | 差別化軸を「Web協働編集・常時検証・リポジトリ連携・OSS」に集中。連携が成立すれば競合でなく合流の選択肢も持つ |
| 無償の作成ツールが既に複数あり「もう一つの無償ツール」に埋没 | 単機能の置き換えではなく「作成→検証→公開→更新」の一気通貫と協働編集で差別化 |

## 8.7 提供形態・OSS方針（確定）

本サービスは **OSS＋コミュニティサポート** を中核に据える（背景は [01-overview](./01-overview.md) 1.4）。

- **ソースコードをOSSとして公開**する。SaaS（マネージド提供）と、自治体・事業者による**自己ホスティング（オンプレ）**の双方を成立させる。
- そのため、特定クラウド固有サービスへの依存を避け、**標準的なミドルウェア（PostgreSQL / S3互換ストレージ / Redis）で完結**する構成を維持する。クラウドのマネージド機能（CDN等）はオンプレ代替（リバースプロキシ＋キャッシュ、MinIO等）を必ず併記する。
- 西沢ツールの出典・功績を**README等で明記**し、敬意を払う。コミュニティからの貢献（ルール追加、インポータ様式対応、翻訳）を受け入れる運用とする。
- **ライセンス（確定）**: アプリ本体 = Apache-2.0（特許条項を含み、自治体・企業のオンプレ採用時の法務レビューを通しやすい）、生成データの推奨ライセンス = CC BY。

### 提供モデル
- **OSS版（自己ホスティング）**: 全機能を無償で利用可能。コミュニティサポート。
- **SaaS版（マネージド）**: ホスティング・運用・サポート付き。利便性に対する対価とし、機能面でOSS版を不当に劣後させない（コア機能はOSSに残す）。
- **SaaS収益はOSS維持の持続可能性資金**と位置づける。OSSの維持コスト（仕様改定追従・セキュリティ対応）を個人の善意に依存させないための構造であり、西沢ツールが示した「個人依存の限界」への構造的な回答でもある。
