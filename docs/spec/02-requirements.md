# 02. 要件定義

## 2.1 ユーザー種別（ロール）

| ロール | 説明 | 主な権限 |
|--------|------|----------|
| システム管理者 | サービス運営者 | 全テナント管理、システム設定、利用統計 |
| 組織管理者（Org Admin） | 事業者/自治体の管理担当 | 組織内ユーザー・プロジェクト管理、公開承認 |
| 編集者（Editor） | データ入力担当 | データ編集、検証、版作成（公開承認は不可、または組織設定による） |
| 閲覧者（Viewer） | 確認担当・関係者 | 閲覧・ダウンロードのみ |
| 公開フィード利用者 | データ利用者（Google等） | 認証不要で公開フィードURLにアクセス |

権限はプロジェクト単位でも上書き可能（例: ある編集者を特定プロジェクトのみ閲覧に制限）。

## 2.2 機能要件

### F-1. プロジェクト・テナント管理
- F-1-1 組織（テナント）を作成し、ユーザーを招待・ロール付与できる。
- F-1-2 組織配下に複数プロジェクト（=フィード）を作成できる。
- F-1-3 プロジェクトを複製（ダイヤ改正の下書き等）できる。
- F-1-4 プロジェクトのアーカイブ・削除（論理削除）ができる。

### F-2. データ取込（インポート）
- F-2-1 GTFS-JP zip（標準GTFS含む）をインポートし、内部モデルへ取り込める。
- F-2-2 西沢ツール様式のスプレッドシート（xlsx）をインポートできる。
- F-2-3 個別CSV（停留所一覧・系統一覧等）をテンプレートに沿ってインポートできる。
- F-2-4 取込時にプレビューと差分（新規/更新/削除）を提示し、ユーザー確認後に反映する。
- F-2-5 取込時の文字コード（UTF-8 / Shift_JIS）・改行コードを自動判定する。

### F-3. マスタ編集
- F-3-1 事業者（agency）を編集できる（日本拡張 `agency_jp` 含む）。
- F-3-2 停留所（stop）を一覧・地図（F-10の地図基盤）の双方で編集できる。標柱と停留所の親子関係を扱える。
- F-3-3 経路（route）を編集できる（日本拡張 `routes_jp` 含む）。
- F-3-4 運賃（fare_attributes / fare_rules）を編集できる。
- F-3-5 営業所（office_jp）・提供情報（feed_info）を編集できる。
- F-3-6 翻訳（translations）を管理できる（停留所名等の読み仮名・多言語）。

### F-4. ダイヤ編集（中核）
- F-4-1 経路に対し系統パターン（停留所の並び・停留所間距離）を定義できる。
- F-4-2 パターンに基づき、便（trip）を時刻入力で追加できる（西沢ツールのダイヤ表に相当する表形式UI）。
- F-4-3 1便の通過時刻を、先頭時刻＋停留所オフセットで自動展開できる。手動上書きも可能。
- F-4-4 ダイヤを表（縦=停留所、横=便）の形式で一覧・一括編集できる。
- F-4-5 運行区分（曜日・期間・例外日）を定義し、便に割り当てられる。
- F-4-6 等間隔運行（frequencies）を任意で定義できる。
- F-4-7 24時を超える時刻（例: 25:10）を扱える。

### F-5. 描画（Shape）
- F-5-1 停留所列から直線結線でshapeを自動生成できる。
- F-5-2 地図基盤（F-10）上で経路線形を手動編集できる。
- F-5-3 （任意）道路ネットワークに沿ったルーティング（map matching）でshapeを生成できる。※外部ルーティングAPI連携、フェーズ2。

### F-6. バリデーション（検証）
- F-6-1 編集中にリアルタイムで整合性チェック（参照切れ・必須未入力等）を行う。
- F-6-2 出力前にGTFS-JP仕様準拠の一括検証を行い、エラー/警告を分類表示する。
- F-6-3 著名な外部検証（MobilityData Canonical GTFS Validator 相当）のルールに準拠した検証を行う。
- F-6-4 致命的エラーがある版は「公開」できない（警告は公開可・要確認）。

### F-7. 出力・配信
- F-7-1 GTFS-JP準拠の `gtfs.zip` を生成・ダウンロードできる。
- F-7-2 版（Revision）を確定し、公開できる。版には版番号・コメント・作成者・施行日を持つ。
- F-7-3 公開フィードを安定URL（最新版エイリアス＋版固定URL）で配信する。
- F-7-4 施行日を指定した予約公開（ダイヤ改正の自動切替）ができる。
- F-7-5 版の差分（前版との比較）を表示できる。
- F-7-6 過去版へのロールバックができる。
- F-7-7 公開した版を**GTFSデータリポジトリ**（gtfs-data.jp、日本バス情報協会協力）へ登録・更新できる（連携設定時）。国内フィードの約半数が同リポジトリ経由で流通し、Mobility Databaseへの反映も行われるため、自前URL配信と並ぶ主要な公開経路として扱う。

### F-8. GTFS-RT（リアルタイム）※フェーズ2以降
- F-8-1 外部の運行情報入力（車両位置API、運行管理システム）を接続できる。
- F-8-2 TripUpdate / VehiclePosition / Alert の各フィードをPBF形式で配信できる。
- F-8-3 静的GTFSの `trip_id` / `stop_id` と動的データの突合（マッチング）を行う。
- F-8-4 運休・経路変更等のAlertを画面から手動投入できる。

詳細は [07-realtime](./07-realtime.md)。

### F-9. 監査・通知
- F-9-1 主要操作（公開・削除・取込）の監査ログを残す。
- F-9-2 公開・検証失敗・施行日到来をメール/Webhookで通知できる。

### F-10. 地図基盤（自前MapLibre）
本サービスは、**自前で用意・運用するMapLibreベースの地図基盤**を採用し、停留所・描画（shape）編集はこの地図上で行う。地図基盤は本サービスとは独立に整備が進む資産であり、現時点で**地図仕様（スタイル/タイル/データ構成）は未確定だが、必要なデータは揃い、仮実装が存在する**。そのため編集機能と地図基盤を疎結合にし、両者の境界（地図アダプタ）を介して連携する。

- F-10-1 停留所・shape編集は、外部タイル（OSM等）ではなく**自前MapLibre地図基盤**を表示面として用いる。
- F-10-2 編集UIは、地図基盤の内部仕様に直接依存せず、**地図アダプタ（Map Adapter）インターフェース**を介して地図と通信する（後述・[04-screens](./04-screens.md) 4.4）。
- F-10-3 地図アダプタは少なくとも次を提供する: 地図の初期化（スタイル/中心/ズーム指定）、マーカー描画・ハイライト、マーカーのドラッグ→座標コールバック、ライン（shape）描画・頂点編集、クリック地点の座標取得、表示領域（bbox）取得、座標へのfly/fit。
- F-10-4 地図基盤の仕様が固まるまでは、アダプタの背後を**仮実装（暫定スタイル/タイル）**で差し替え可能とし、編集機能の開発をブロックしない。
- F-10-5 地図基盤がオフライン/未提供の環境（自治体オンプレ等）でも、編集自体（座標の数値入力・一覧編集）は継続できるよう、地図はあくまで補助手段とする（座標の真実は数値データ）。
- F-10-6 （任意・将来）地図基盤側のデータ（道路ネットワーク等）を活用したmap matching（F-5-3）への接続点をアダプタに設ける。

> 地図基盤側の要件（レイヤ構成・追加データ・スタイル・配信）は [09-basemap](./09-basemap.md) に定義する。本章では「編集機能が地図基盤をどう利用するか」の契約（アダプタ）を定義し、地図仕様の確定を待たずに編集機能を実装可能にする。

## 2.3 非機能要件

| 区分 | 要件 |
|------|------|
| 可用性 | 公開フィード配信は 99.9% を目標。配信はCDN/オブジェクトストレージ前段でアプリ障害時も継続可能とする。 |
| 性能 | 1フィードあたり停留所〜数千、便〜数万を想定。ダイヤ表編集はクライアント側で快適に動作（仮想スクロール）。`gtfs.zip` 生成は数万便でも数十秒以内。 |
| スケール | マルチテナント。組織数〜数千、プロジェクト数〜数万を想定。 |
| セキュリティ | 認証（OIDC/メール）、RBAC、保存データ暗号化、公開フィードのみ匿名アクセス可。監査ログ。 |
| 国際化 | UIは日本語優先（将来i18n）。データは多言語translations対応。 |
| 文字コード | 入力はUTF-8/Shift_JIS受入、内部・出力はUTF-8（BOMなし、LF）。 |
| 互換性 | 出力はGTFS-JP最新版（**v4**・2025年度改訂）に準拠。旧第3版系・標準GTFSのみの出力モードもプロファイルとして持つ。 |
| アクセシビリティ | 主要画面はキーボード操作・スクリーンリーダ配慮（WCAG 2.1 AA目標）。 |
| 法令・ライセンス | 公開データの推奨ライセンス（CC BY 等）を表示・選択可能とする。 |

## 2.4 制約・前提

- GTFS-JPの仕様改定に追従できるよう、ファイル/項目定義は設定駆動（バージョン定義テーブル）とする。
- 西沢ツールの様式はバージョン差があるため、インポータは様式バージョンを判定・吸収する。
- GTFS-RTは入力ソース（ロケーションシステム）の存在が前提であり、本サービス単独では生成しない。
